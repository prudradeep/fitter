| --- | --- | --- | --- | --- | --- | --- | --- |

2. Critical dimensions answer: the only mitigation critical grounding dimensions are `hazard_fit` and `justification_soundness`. [app/services/chat_service.py :: ChatService] [app/services/validation_service.py :: _score_mitigation_grounding()]

3. Threshold answer: there is no mitigation equivalent of a hazard `VALIDATION_THRESHOLDS` constant. The mitigation threshold is `minimum_supported = _minimum_supported_mitigation_dimensions(len(critical_dimensions), validation_mode)`: strict returns the critical dimension count, so `2` of `2`; easy returns `max(1, critical_dimension_count - 1)`, so `1` of `2`. The retrieval support score floor is `settings.mitigation_support_score_floor`, default `0.15`, and easy mode uses `max(0.05, floor * 0.5)`, so default `0.075`. [app/services/validation_service.py :: _minimum_supported_mitigation_dimensions()] [app/services/validation_service.py :: _mitigation_support_score_floor()] [app/config.py :: Settings]

4. Contradiction answer: confirmed. Mitigation user evidence calls `_validate_user_evidence_against_core_kb()` with `claim_type="mitigation"`; that uses `EvidenceContradictionService.validate_evidence_against_kb()`. If the returned verdict is not `VALID`, mitigation returns `REJECT` for `INVALID` and `ABSTAIN` otherwise before strict/easy scoring is reached. [app/services/validation_service.py :: _validate_mitigation_against_stats()] [app/services/validation_service.py :: _validate_user_evidence_against_core_kb()] [app/services/evidence_contradiction_service.py :: validate_evidence_against_kb()]

5. Flatline/clarification answer: mitigation uses a parallel clarity-turn mechanism, not the hazard flatline implementation. `mitigation_clarity_turn_cap = 5`; each unresolved mitigation clarity prompt increments `session.mitigation_clarity_turns` by `1`; if `session.mitigation_clarity_turns >= 5`, temporary evidence is discarded, clarity state is cleared, the phase returns to `mitigation_measure`, and the user must resubmit. A separate repeated-question check can emit `Clarification still needed`, but it is still the mitigation clarity path. [app/services/chat_service.py :: ChatService] [app/services/chat_mitigation_creation_workflow.py :: _run_mitigation_clarity_track()]

6. Duplicate-status answer: duplicate status is a separate mitigation check, not a scored grounding dimension. The local duplicate check searches existing mitigation records for the selected hazard and returns a duplicate payload; the semantic duplicate check asks an LLM to compare against existing measures; the mitigation measure step branches to a duplicate suggestion step before clarity and grounding. # Investigation 3 - Does Self-Evaluation Modulate STSI Strictness?

1. Definitive answer: yes, self-evaluation affects STSI behavior, but only probe candidate context/selection, not pass thresholds or adjudication strictness. [app/services/chat_mitigation_creation_system_observations.py :: _system_inquiry_observations()] [app/services/chat_mitigation_creation_system_attributes.py :: _system_inquiry_candidate_llm_payload()] [app/services/chat_mitigation_creation_system_flow.py :: _system_inquiry_profile()]

2. Storage origin: `_handle_evaluation_answer()` appends each answer to `session.evaluation_answers` and stores it as a `UserQuestionResponse` tied to `session.mitigation_record_id`; `_evaluation_complete_step_with_llm()` then renders the evaluation summary and starts the STSI intro path. [app/services/chat_mitigation_creation_evaluation.py :: _handle_evaluation_answer()] [app/services/chat_mitigation_creation_evaluation.py :: _evaluation_complete_step_with_llm()]

3. Probe-selection mechanism: `_system_inquiry_systemic_score()` reads `session.evaluation_answers`, selects answers whose category/question/chart title contains `systemic` or `structural`, converts their `score` to integers, and returns the maximum or `0`. `_system_inquiry_observations()` adds probe `A5-P1` when that score is `>= 7` and extracted `leverage_depth` is `parameter`. The added probe has salience `75` and an anchor `self_eval_score`. [app/services/chat_mitigation_creation_system_attributes.py :: _system_inquiry_systemic_score()] [app/services/chat_mitigation_creation_system_observations.py :: _system_inquiry_observations()]

4. Candidate-review mechanism: the STSI candidate LLM payload includes `evaluation_answers` in the dossier used by candidate screening, verification, and corpus adjudication. Therefore self-evaluation answers can influence which candidates survive LLM screening/verification/corpus review, but the code does not assign a literal formula from evaluation score to candidate rank except for the `A5-P1` trigger above. [app/services/chat_mitigation_creation_system_attributes.py :: _system_inquiry_candidate_llm_payload()] [app/services/chat_mitigation_creation_system_attributes.py :: _system_inquiry_screen_candidates_with_llm()] [app/services/chat_mitigation_creation_system_attributes.py :: _system_inquiry_verify_candidates_with_llm()] [app/services/chat_mitigation_creation_system_attributes.py :: _system_inquiry_adjudicate_corpus_with_llm()]

5. Probe-count answer: self-evaluation does not raise the cap. The cap remains `2` when no prior same-hazard measures exist and `3` when prior same-hazard measures exist. [app/services/chat_mitigation_creation_system_observations.py :: _system_inquiry_observations_with_llm()]

6. Adjudication-strictness answer: self-evaluation answers are included in the context fingerprint and stored payload, but the completion profile uses annotation resolution-state weights, and response adjudication evaluates the user response to the current observation. No score-derived higher pass bar is applied in STSI completion. [app/services/chat_mitigation_creation_system_flow.py :: _system_inquiry_context_snapshot()] [app/services/chat_mitigation_creation_system_flow.py :: _system_inquiry_profile()] [app/services/chat_mitigation_creation_system_flow.py :: _append_system_inquiry_annotation()]

# Investigation 4 - STSI Probe Count and Selection

1. Probe count answer: STSI runs up to `2` probes for a mitigation measure with no prior same-hazard mitigation rows, and up to `3` probes when prior same-hazard mitigation rows exist. The cap is context-dependent and hard-coded; no setting controls it. [app/services/chat_mitigation_creation_system_observations.py :: _system_inquiry_observations()] [app/services/chat_mitigation_creation_system_observations.py :: _system_inquiry_observations_with_llm()]

2. Probe source answer: probes are both hand-built and library-backed. `_system_inquiry_observations()` builds core candidates directly from measure, hazard, target groups, validation gaps, extracted attributes, affected groups, and prior measures; `_system_inquiry_additional_library_observations()` then draws extra triggered probes from `system_inquiry_probe_library.json`. The library loader requires at least `30` probes and builds a `records` map by `probe_id`. [app/services/chat_mitigation_creation_system_observations.py :: _system_inquiry_observations()] [app/services/chat_mitigation_creation_system_observations.py :: _system_inquiry_additional_library_observations()] [app/services/system_inquiry_probe_library.py :: system_inquiry_probe_library()]

3. LLM role answer: the LLM does not generate arbitrary final probes in this path. In the LLM path, it extracts measure attributes, then screens existing candidates, assigns `verify_votes` from `0` to `3`, and adjudicates `corpus_label` as `evidenced`, `unproven`, or `refuted`. [app/services/chat_mitigation_creation_system_attributes.py :: _system_inquiry_measure_attributes_with_llm()] [app/services/chat_mitigation_creation_system_attributes.py :: _system_inquiry_screen_candidates_with_llm()] [app/services/chat_mitigation_creation_system_attributes.py :: _system_inquiry_verify_candidates_with_llm()] [app/services/chat_mitigation_creation_system_attributes.py :: _system_inquiry_adjudicate_corpus_with_llm()]

4. Screening and thresholds answer: finalization discards candidates with no `probe_id`, duplicate candidate keys, missing required anchors, `corpus_label == refuted`, or instability. A candidate is unstable when `screen_result is False` or `verify_votes < 2`; `verify_votes=None` is not unstable. If prior surfaced annotation count is `>= 10`, candidates with `salience_score < 0.9` are held by cap before selection. [app/services/chat_mitigation_creation_system_observations.py :: _system_inquiry_finalize_candidates()] [app/services/chat_mitigation_creation_system_observations.py :: _system_inquiry_candidate_is_unstable()]

5. Ranking answer: candidates are sorted by `(-group_count, evidence_rank, family_rank, -salience)`, where `evidence_rank` is `0` for `evidenced` and `1` otherwise, `family_rank` is `0` for `D_portfolio` and `1` otherwise, and salience is the integer candidate salience. Selection allows at most `2` candidates per family and stops at the cap. If prior measures exist, `_system_inquiry_ensure_portfolio_selection()` forces one `D_portfolio` candidate into the selected set when one is available, replacing the last non-portfolio selected candidate if the cap is already full. [app/services/chat_mitigation_creation_system_observations.py :: _system_inquiry_candidate_rank_key()] [app/services/chat_mitigation_creation_system_observations.py :: _system_inquiry_finalize_candidates()] [app/services/chat_mitigation_creation_system_observations.py :: _system_inquiry_ensure_portfolio_selection()]

6. Deduplication answer: within a candidate set, `_system_inquiry_candidate_dedupe_key()` deduplicates by `probe_id` plus canonicalized anchors. Across prior measures, `_apply_system_inquiry_prior_dedupe_reuse()` builds a reuse map from current prior annotations keyed by `probe_id` plus canonical anchors; if a matching prior response exists, the current candidate records `dedupe_basis`, prior annotation metadata, and rewrites the observation/question to reference the prior response instead of dropping the concern. Context changes are tracked by `context_fingerprint`; old annotations whose fingerprint differs are copied to `superseded_annotations` with `status="superseded"`. [app/services/chat_mitigation_creation_system_observations.py :: _system_inquiry_candidate_dedupe_key()] [app/services/chat_mitigation_creation_system_observations.py :: _apply_system_inquiry_prior_dedupe_reuse()] [app/services/chat_mitigation_creation_system_flow.py :: _system_inquiry_superseded_annotations()]

7. Skip answer: the user skips at the STSI intro by selecting `Skip system inquiry`; the handler sets `session.system_inquiry_skipped = True` and calls completion with `skipped=True`. The persisted STSI payload includes `"skipped": bool(session.system_inquiry_skipped)`, so a skip is distinguishable afterwards from a completed probing round. [app/services/chat_options.py :: SYSTEM_INQUIRY_INTRO_OPTIONS] [app/services/chat_mitigation_creation_system_flow.py :: _handle_system_inquiry_intro()] [app/services/chat_mitigation_creation_system_flow.py :: _system_inquiry_payload()]

8. Output-shape answer: STSI stores per-measure JSON in `UserMitigationMeasure.system_inquiry_json` with schema version, library version, skipped flag, summary, selected hazard, mitigation measure, context fingerprint/snapshot, attributes, coverage summary, held observations, candidate audit, profile, telemetry, annotations, and superseded annotations on re-run. The PDF reaches that data through each selected `UserMitigationMeasure.system_inquiry_json`, using annotations in the gaps section and summary/profile-derived fields in measure and comparison content. [app/services/chat_mitigation_creation_system_flow.py :: _system_inquiry_payload()] [app/services/chat_mitigation_creation_system_flow.py :: _persist_system_inquiry_result()] [app/services/report_export.py :: _system_inquiry_summary_lines()] [app/services/report_export.py :: _measure_card_payload()]
